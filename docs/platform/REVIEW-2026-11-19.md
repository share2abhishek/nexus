# Requirements review: product owner, software architect, QA (19 Nov 2026)

**Reviewed:**
- `docs/platform/ROADMAP.md`
- `docs/platform/ACCESS-AND-ENTITLEMENTS.md`
- `docs/billing/ACCESS-REQUIREMENTS.md`
- `docs/billing/PLAN.md`
- `docs/billing/REQUIREMENTS.md`
- the `access-control`, `tenant-isolation`, `usage-limits` and `billing-*` skills

**Method:** each document read from three seats: an experienced **product owner** (value, scope, order, customers), a
**software architect** (foundations, risk, operability) and **QA** (testability, environments, release gates). The facts
below were verified on 19 Nov 2026 in the code and, read-only, on production.

**Outcome:** the requirements are thorough and internally consistent (after the C1–C24 reconciliation). The main problems are
**order and readiness**, not content:
- revenue arrives too late;
- the quality gates the plan depends on don't exist yet: no CI run, no staging, a red test suite;
- the scope is large for a platform with 3 organisations.

The **revised priority** in section 5 has been applied to `ROADMAP.md`.

## 3. Software architect review

| # | Severity | Finding | Recommendation |
|---|---|---|---|
| AR1 | **High** | **Every commit to `master` deploys** (post-commit hook), but phases are multi-week and multi-commit. Half-built phases would reach production. | Build each phase on a branch `feature/<phase>`. Merge to `master` only when the phase gates pass. Everything ships dark behind its switch (already the rule). The hook stays on `master` only. |
| AR2 | **High** | **No CI** (F4). | **Q0:** port `.github/workflows/test.yml` to `bitbucket-pipelines.yml` (Node 20, SQLite leg, Postgres 16 service leg). Run it on every branch and pull request; merge only when green. The deploy stays local (as today). |
| AR3 | **High** | **Foundation order.** The access engine (A0) is cheap and everything depends on it. Tenancy (T1) is large, and blocking revenue behind it is not justified at 3 organisations, **provided** the S0 isolation harness shows no real leak. | S0 then A0 first. T1 becomes a **parallel track** after A0, module by module. Any real cross-organisation leak found by the S0 harness is fixed immediately (P0), not scheduled. The T1 leads/CRM module must finish before R1 (scope filters). New tables (billing, roles, usage) are born with `org_id` / `account_id`. |
| AR4 | **Medium** | **Scope against team size.** Two bounded modules with ports, row-level security, staff MFA, four staff roles, plan revisions, add-ons and AI agents is a lot to build and maintain for 3 organisations. | Keep the module boundaries (cheap now, costly later). Defer row-level security, the extra staff roles, add-ons and AI agents (Waves 4 and 5). Keep plan revisions: they are cheap and protect invoices. |
| AR5 | **Medium** | **Migrations on production Postgres:** `org_id` on about 60 tables. | Always additive: nullable column, backfill, verify, then `NOT NULL` a week later. Batch per module. The deploy script's `pg_dump` backup runs before each one (it already does). Rehearse on staging with a production copy (QA2). |
| AR6 | **Medium** | **Files on the container's local disk** (`data/media`). Storage quotas, per-organisation paths and deletion depend on a file registry. | Confirm the media folder is a mounted volume included in backups. L1's files service is the single writer. Keep S3 as a port implementation for later; don't build it now. |
| AR7 | **Medium** | **Server-driven menu** (B1) changes a static ~36-item sidebar in `public/index.html` that global scripts touch. | Render from `/api/me/menu`, with the static sidebar as fallback and cached last menu. Migrate group by group. Snapshot tests per role × plan. A browser smoke test (QA5). |
| AR8 | **Medium** | **Two editions** (desktop SQLite, server Postgres) double every path. | Desktop gets a fixed "desktop plan" through the same engine (as the spec says) and none of the billing or staff screens. Test desktop only for "unchanged behaviour" (characterization). |
| AR9 | **Medium** | **E-mail is now business-critical** (alerts, invoices, dunning). | Before B5a: confirm the production SMTP sender's domain authentication (SPF, DKIM), a bounce log, and a "send test e-mail" action in the staff console. |
| AR10 | Low | Caching and versions are designed for one process (one container today). | Fine. If a second instance is added, the version check already covers it (the database is the source); no in-memory-only invalidation is relied on. |
| AR11 | Low | Two audit tables (C15). | Fine. Keep one merged read view. |
| AR12 | Medium | **India DPDP Act:** personal data in audit rows, usage logs and organisation deletion. | Data map per table (personal or not). Retention: audit 2 years; usage events 13 months; deletion after closure in 30 days (already in the spec). Add the DPDP mapping to the privacy page in B8. |

## 5. Revised priority (applied to `ROADMAP.md`)

**Principle:**
1. protect what exists;
2. lay the minimum foundation once;
3. sell by feature;
4. get paid;
5. alert;
6. then control and scale.

**Rules:**
- Count usage early, because enforcement needs a month of data.
- Tenancy hardening runs alongside, not in front.

| Wave | Goal | Phases (in order) | Business result |
|---|---|---|---|
| **0 Now** (this week) | Keep customers running; make releases safe | **Owner action:** extend or set Avinash Group's plan before 2 Dec (PO1). **Q0** quality gates (CI on Bitbucket, quarantine, staging). **S0** safety net | Bot keeps answering; every later phase can be tested |
| **1 Sell by feature** | Plans by feature, and the foundation | **A0** access engine → **B0** catalogue and plan designer → **B1** feature gate, menu, upgrade prompts → **B5a** expiry and overdue alerts → **L2a** AI usage counting (count only) | Custom plans like "Website AI chat"; menus lock and unlock; customers get warned before expiry; AI cost per organisation known |
| **2 Get paid** | Money in | **B3** invoices and offline payments (activate plan) → **B2** wallet → **B4** Razorpay online and the customer Billing page (old client removed) | Bank or UPI payments recorded with proper invoices; customers pay online |
| **3 Team and oversight** | Roles, support, health | **R1** roles v2 (sales and support agents, scope) and support sessions → **S1** staff console and organisation health. **T1** tenancy hardening as a parallel track from Wave 1 (leads module before R1) | Sales teams with assigned chats; audited support; one view of every organisation |
| **4 Limits and lifecycle** | Fair use and plan changes | **L1** limits and storage (warn first) → **B6** message metering → **B5b + P1** upgrade, downgrade, cancel, plan change handling, lockout switch → **B7 + L2b** AI credits enforcement and top-ups | Usage screens; upgrades pay the difference; AI credits enforced after a month of data |
| **5 Growth** | Differentiators | **R2** custom roles and teams → **R3** AI sales agents → **B8** reports and add-ons → **T2** row-level security | Advanced roles, AI agents, revenue reports |

**MVP = Waves 0 to 2.** Waves 3 to 5 are re-prioritised after the MVP with customer feedback. PO6 may pull R1 forward.

**Changes from the previous order:**

| Item | Previous | Now | Why |
|---|---|---|---|
| Q0 quality gates | – | Wave 0 | AR2, QA1, QA2, QA4 |
| T1 tenancy | phase 3, blocking | parallel track | AR3: revenue isn't blocked; leaks found are still P0 |
| Expiry alerts | inside B5 (phase 12) | **B5a**, Wave 1 | PO4 |
| AI usage counting | inside B7 + L2 (phase 16) | **L2a**, Wave 1 (count only) | a month of data is needed before pricing and enforcing |
| B3 before B2 | B2, then B3 | B3, then B2 | offline invoices don't need the wallet; B4 does (money never lost) |
| R1 / S1 | Wave "roles" before money | after money | PO3, unless PO6 |
| B5 lifecycle | one phase | B5a early, B5b + P1 later | PO4 |
| L2 | one phase with B7 | L2a count early, L2b enforce with B7 | data first |
